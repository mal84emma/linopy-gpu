**Phase:** 2→3   **Raised:** 2026-08-22T21:55Z   **Trigger:** E1 (3/2 planner split on user-visible API behaviour)
**Question:** On a machine where `cuopt-cu12` is installed but no usable GPU exists, should `linopy.available_solvers` omit cuOpt (GPU probe inside `is_available()`), or contain it with the GPU check deferred to `_license_probe()`/solve time?
**Options:** A) probe in `is_available()` — GPU-less machines omit cuopt from `available_solvers` (plans 1, 2, 4). Consequence: matches §4.6 c3 verbatim; costs a CUDA device probe at listing time and leaves the generic "not installed" assert text on solve. B) import probe only, GPU check in `_license_probe()` (plans 3, 5). Consequence: matches cuPDLPx precedent (I5) and the `_AvailableSolvers` documented contract; but `available_solvers` then advertises cuopt on GPU-less machines.
**Evidence for each:** A: charter §4.6 constraint 3 — "On a machine with the package but no GPU, or the wrong driver, `linopy.available_solvers` must simply omit cuOpt" — stated as **binding by the human lead**. B: `linopy/solvers.py` cuPDLPx `is_available` is an import probe; `test_available_solvers.py:39`; plans 3/5's `_AvailableSolvers` contract argument.
**Resolve-first steps taken:** (1) repo precedent read — cuPDLPx import-probes, but no GPU solver today satisfies §4.6; (2) no spike needed — both behaviours characterised in exploration §13/Surprises; (3) PR #516 checked by planners — same import-probe pattern, predates §4.6; (4) cuOpt docs — `import cuopt` succeeds GPU-less by design; (5) logged here.
**Recommendation:** **A.** §4.6 is explicitly marked binding by the human lead and its constraint-3 sentence prescribes exactly this observable behaviour; I5 is a style invariant and yields to an explicit product requirement. Not a judgment call in the §3.7 sense — the charter text pre-decides it.
**Blocked:** Nothing.
